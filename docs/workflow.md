# 개발 진행 절차

## 변경 단위

[변경 양식](changes/TEMPLATE/intent.md)을 복사해 docs/changes/<ID>-<이름>/에 intent·spec·plan·evidence를 유지한다.

1. intent: 사용자 문제, 원하는 결과, 범위, 제약과 미해결 질문.
2. spec: 동작, 설계, 오류 처리, 수용 기준과 위험.
3. plan: 변경 파일, 순서, 검증과 되돌리기.
4. 구현과 점검: 계획과 구현을 함께 갱신하고 실제 결과를 evidence에 기록.
5. 리뷰와 배포: [REVIEW.md](../REVIEW.md)와 [release.md](release.md) 적용.
6. 유지보수: 반복 문제를 [장애 양식](incidents/TEMPLATE.md)과 회귀 검사에 연결.

## 이번 작업과 다음 작업

- 000-project-bootstrap: 사용자가 요청한 문서·규칙·변경 기록 초기 구성.
- 001-generation-spike: 사용자 수락 후 첫 Python CLI 생성·픽셀 변환 시제품 구현 및 검증.
- 002-portable-execution: 다른 PC 이동·원격·클라우드 생성 요구를 문서와 첫 시제품 초안에 반영. 실제 통합 실행은 아직 미검증.
- 초기 구성의 수락을 전체 앱·모델 설치·배포 승인으로 확대하지 않는다.
- 이미 명시된 사용자 요구와 승인 범위는 재질문하지 않고 근거를 기록한다.
- 문서의 초안·체크박스·AI의 자체 점검은 사용자의 승인으로 간주하지 않는다.
- 범위 안의 일상적인 구현 판단은 수행하고, 범위·데이터·외부 비용을 크게 바꾸는 결정만 별도 확인한다.

## 검토 기록

승인자, 날짜, 범위와 근거를 기록한다. 이 저장소에서는 현재 채팅의 사용자 발언을 날짜·짧은 원문과 함께 남길 수 있다. 확인되지 않은 대화 ID나 링크를 만들어 넣지 않는다.

사용자가 첫 구현을 요청하거나 계획을 수락하면 그 실제 표현에 해당하는 범위를 기록한다. 독립 리뷰가 없다면 자체 점검만 했다고 명시한다.

## 검증 피드백

- 규격 검증과 픽셀아트 표현 평가는 분리한다.
- 앱 코드 검사는 실패 시 0이 아닌 종료 코드를 반환한다.
- 버그는 가능한 경우 먼저 예상한 이유로 실패하는 재현을 만든다.
- 앱 검증 도구가 없으면 첫 구현 계획에 도구 구성과 최초 실행을 포함한다.
- UI 변경에서는 실제 화면과 상호작용을 확인한다.
- 모델·워크플로·프롬프트 변경에서는 기존 입력과 출력 품질을 비교한다.
- 실행하지 않은 검사나 생성하지 않은 이미지는 통과했다고 기록하지 않는다.

## 자동화 도입

단일 작업과 수동 검토로 시작한다. 실제 로컬 검증 후 005 변경으로 GitHub Actions CI를 추가한다. PR·main push에서 OS·Python별 설치·테스트·빌드·CLI를 자동 확인한다. 브랜치 보호·Hooks·eval 자동화는 아직 설정하지 않았다.

플레이북의 병렬 세션, 상시 모니터링, 조직용 관리 설정은 자동으로 도입하지 않는다. [적용 근거](references/sdlc-playbook.md)를 참고한다.

## 작업 단위별 PR

사용자의 2026년 10월 31일 요청으로 작업 단위마다 codex/ 브랜치에서 검증 후 PR을 제출한다. 원격 저장소가 비어 있어 빈 초기 커밋을 main에 두고 시작했다. 최초 시제품을 첫 PR로 제출하고 후속 변경은 별도 PR로 구분한다. 선행 PR에 의존하면 그 브랜치를 base로 삼아 차이와 병합 순서를 명시한다. 생성물·모델·인증 정보는 올리지 않는다. 실제 검토와 병합은 사용자 결정으로 남긴다.
